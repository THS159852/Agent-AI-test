# Test Case Reviewer

Review **existing** test cases from `testcase-generator`. Do **not** rewrite the full suite unless the user asks for fixes. Follow `docs/QA_GLOBAL_RULES.md` and the rules in `skills/testcase-generator/SKILL.md`.

**Mandatory:** rebuild and score a **coverage matrix** from the source spec during review. Do **not** accept a generator coverage summary as proof. Do **not** give Pass / Pass with fixes until every required matrix row is scored.

## Required inputs

| Input | Required | Source |
|-------|----------|--------|
| Generated test cases | **Yes** | Chat output, `@file`, Excel, or pasted table |
| Original requirements / AC / BR | **Yes** (preferred) | Same sources used to generate |
| API spec / handler / data-mapping notes | When API or merge/mapping rules exist | OpenAPI, technical spec, table-merge rules, flags |
| UI / browser document | When UI cases exist | Mockups, `browser-test-document.md`, screenshots |
| Coverage summary from generator | Optional | Never treat as complete; rebuild the matrix from source |

If requirements are missing, review **format/quality only**, mark source-alignment and matrix findings as `Blocked — missing source`, and ask for the source files. Do **not** mark Covered from titles alone.

## Workflow

```
Progress:
- [ ] Step 1: Inventory screens and map every TC
- [ ] Step 2: Quality gate (format / language / structure)
- [ ] Step 3: Source alignment (requirement match)
- [ ] Step 4: Coverage matrix (AC / Rule / Endpoint / Branch) — mandatory
- [ ] Step 5: Coverage & mismatch analysis (per screen)
- [ ] Step 6: Write review report (grouped by screen)
```

### Step 1: Inventory screens and map every TC

Build a **Screen Registry** before scoring findings:

| Screen ID | Screen name | URL / route (if known) | Module column values | TC IDs on this screen |
|-----------|-------------|------------------------|----------------------|------------------------|

**How to resolve screen:**

1. Prefer `Module` column when it names a screen/feature.
2. Else derive from Steps (`Navigate to /login` → Login screen).
3. Else from Requirement Ref / browser doc `SCR-###`.
4. Else from Title subject (`Verify login…` → Login).
5. If still unclear → Screen = `Unmapped` and raise a finding.

Every finding **must** include **Screen**.

### Step 2: Quality gate

Check each test case against generator + global rules:

| Check | Fail when |
|-------|-----------|
| Language | Any column not English (esp. Expected Result) |
| Title | Missing `Verify` prefix, or chains unrelated checks with "and" |
| ID | Missing / duplicate / wrong convention |
| Requirement Ref | Empty and not marked `[Derived]` |
| Steps | Vague ("perform login"), not numbered, missing data |
| Expected Result | Vague ("works correctly", "OK", "as expected") **or** status-only (`HTTP 200`, "success") when the AC specifies mapped fields, table merge, token, flag, or payload |
| Test Data | Placeholder-only (`valid email`) instead of concrete values |
| Priority / Type / Auto Candidate | Missing or inconsistent with risk |
| One verification | One TC asserts multiple unrelated outcomes |

### Step 3: Source alignment

For each TC, compare Steps + Expected Result to the cited AC/BR/UI:

| Issue type | Meaning |
|------------|---------|
| **Mismatch** | Expected result or steps contradict the requirement / observed UI |
| **Over-spec** | Invents rules not in source (e.g. max length 50 when unspecified) |
| **Under-spec** | Requirement exists but Expected Result is too weak to verify it (incl. HTTP 200 only) |
| **Wrong screen** | TC content belongs to another screen than Module/Steps claim |
| **Stale / N/A** | Tests out-of-scope or removed behavior |
| **Duplicate** | Same condition covered by another TC |
| **Assumed coverage** | One TC treated as covering a similar but different branch, flag, merge, or endpoint |

Never invent missing business rules — list them under Questions.

### Step 4: Coverage matrix (mandatory)

Run this **before** writing the verdict. Build the matrix from the **source spec**, not from the TC pack. If the generator already printed a matrix, **rebuild it** and compare claimed-vs-actual.

**Rows (one per distinct condition — do not collapse similar ones):**

- Every acceptance criterion
- Every business rule / decision branch
- Every API endpoint and specified success/error path
- Every specified flag, setting, token flow, table-merge, or data-mapping variant

**Template:**

| AC / Rule / Endpoint / Branch | Screen | Pos | Neg | Bnd | Role | Data/mapping asserted | TC IDs | Covered |
|-------------------------------|--------|-----|-----|-----|------|------------------------|--------|---------|
| AC-1 valid login | Login | ✓ | | | | Session + redirect | LOGIN-TC-001 | Yes |
| POST /x merge tables A+B | API | ✓ | | | | Merged row fields | — | **No** |

- Pos / Neg / Bnd / Role: mark `✓` when a TC exists, `—` if N/A in source, **empty / No** if required but missing.
- **Data/mapping asserted:** `Yes` only if Expected Result checks the specified fields, merge, token, or flag — not status code alone.
- **Covered = Yes** only when (1) a TC maps to **that exact** row and (2) Data/mapping asserted = Yes for rows that specify data/mapping.

**Scoring rules (miss-case gates):**

| Gate | Fail when | Finding |
|------|-----------|---------|
| Status ≠ coverage | TC only asserts HTTP 200 / "success" while spec defines mapped fields, table merge, token, or payload | Under-spec; row **not Covered** |
| Happy path ≠ edge | A specified valid branch (flag, setting, token flow) was skipped or labeled edge/"do later" | Coverage gap; treat as **Positive P0/P1**, not edge |
| Similar ≠ same | Reviewer or pack assumes one TC covers a sibling branch (different merge table, flag, endpoint, or outcome) | Assumed coverage; **separate row** required |
| One happy case / API | Pack has one success TC per endpoint and skips other specified success branches | Coverage gap; **Rework required** if any required Pos row is empty |
| Matrix skipped | Review exports findings without completing this matrix | **Do not** Pass; complete the matrix first |

Map every existing TC ID onto matrix rows. Unmapped TCs → traceability finding. Uncovered required rows → Coverage gaps with a suggested `Verify …` title.

### Step 5: Coverage & mismatch analysis (per screen)

For **each screen**, use the matrix plus:

| Dimension | Look for |
|-----------|----------|
| AC coverage | AC on this screen with no TC, or Covered = No |
| Positive / Negative / Boundary | Missing for validated fields |
| Permission / Role | Missing when roles are in scope |
| UI vs API mix-up | UI expected results on API-only AC (or reverse) |
| Traceability | TC cites wrong AC or no AC |
| Priority skew | Critical happy path as P2/P3, or trivial as P0 |
| Weak assertion | Status-only Expected Result on a mapping/merge row |

### Step 6: Write review report

Report language: match the user (Vietnamese if they asked in Vietnamese). Keep **TC IDs and Titles in English** as authored.

Use this template:

```markdown
## Test Case Review Summary
- Sources reviewed: <files / docs>
- Total test cases: N
- Screens covered: M
- Matrix rows: R (Covered Yes / No / N/A)
- Uncovered required rows: U
- Findings: Critical C / Major Ma / Minor Mi
- Verdict: Pass | Pass with fixes | Rework required

## Screen Registry
| Screen ID | Screen name | TC count | Finding count |
|-----------|-------------|----------|---------------|

## Coverage matrix
| AC / Rule / Endpoint / Branch | Screen | Pos | Neg | Bnd | Role | Data/mapping asserted | TC IDs | Covered |
|-------------------------------|--------|-----|-----|-----|------|------------------------|--------|---------|

## Findings (by screen)

### Screen: <Screen name> (<Screen ID>)
| Finding ID | Severity | TC ID | Title | Issue type | Problem | Evidence (AC/UI) | Suggested fix |
|------------|----------|-------|-------|------------|---------|------------------|---------------|
| REV-001 | Critical | LOGIN-TC-003 | Verify … | Mismatch | … | AC-2 | … |

### Screen: Unmapped
| … |

## Coverage gaps (by screen)
| Screen | Missing condition | Related AC/BR | Matrix row | Suggested new TC title |
|--------|-------------------|---------------|------------|------------------------|

## Quality defects (cross-screen)
| Finding ID | Severity | TC ID | Screen | Problem | Suggested fix |
|------------|----------|-------|--------|---------|---------------|

## Duplicates / assumed coverage
| TC A | TC B or skipped sibling | Screen | Same condition? | Why separate (flag / merge / endpoint) |
|------|-------------------------|--------|-----------------|----------------------------------------|

## Assumptions / Questions / Risks

## Suggested next steps
1. Fix Critical/Major findings in place, or re-run `testcase-generator` for uncovered matrix rows / affected screens only
2. Re-run this skill on the updated pack (rebuild the coverage matrix)
3. Optional: `testdata-generator` / `automation-script-writer` after Pass
```

### Severity

| Severity | Use when |
|----------|----------|
| **Critical** | Wrong expected result vs AC; security/permission hole; wrong screen that would fail execution; uncovered P0 happy-path / mapping row |
| **Major** | Missing P0/P1 matrix coverage; status-only assertion where spec requires data/mapping; invented rule; unusable steps; non-English Expected Result; assumed coverage of a distinct branch |
| **Minor** | Wording, ID style, Auto Candidate, non-blocking duplicate nuance |

### Verdict rules

| Verdict | When |
|---------|------|
| **Pass** | Matrix complete; no uncovered required rows; no Critical/Major; Minor optional |
| **Pass with fixes** | Matrix complete; only Minor, or Major that is a quick in-place patch (not missing branches) |
| **Rework required** | Matrix not completed; any uncovered required Positive/P0 row; any Critical; or Major covering ≥1 full screen / AC cluster / distinct branch |

## Anti-patterns

| Avoid | Do instead |
|-------|------------|
| Regenerating all TCs by default | Report findings; regenerate only if user asks |
| Findings without Screen | Always set Screen / `Unmapped` |
| Vague "testcase is wrong" | Cite TC ID + AC/UI evidence + suggested fix |
| Silent invented rules during review | Flag as Over-spec or ask Questions |
| Ignoring Module vs Steps conflict | Raise **Wrong screen** |
| "HTTP 200 is done" | Require Expected Result to assert mapped fields / merge / token / flag from the spec |
| Demoting specified valid branches to edge/"do later" | Score them as Positive P0/P1 matrix rows |
| Assuming similar cases share one TC | Separate rows for different flags, merges, endpoints, or outcomes |
| One happy case per API | Cover every specified success branch before Pass |
| Skipping the coverage matrix / trusting generator summary | Rebuild and score the matrix from source before any verdict |
